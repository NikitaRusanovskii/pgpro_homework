## Ошибки в логике
- Неправильное условие `!=` в parse_operation:
`!((*pos) + 1 >= len && data[(*pos) + 1] == '=')` при раскрытии отрицания получим
`(*pos) + 1 < len || data[*pos + 1] != '='`.
Первое условие - верно практически всегда.
Второе условие - выход за границу массива.
Ошибка работы функции:

## Архитектурные решения

- static int32 compare(Oid type, Datum obj1, Datum obj2, Oid collation):
Функция хорошая, полностью реализует требуемую функциональность.
Предложение: можно попробовать использовать кеширование типов PostgreSQL, чтобы получить информацию о функции сравнения(Следует проверить её Oid, если он невалидный, значит, функции сравнения нет. Однако для базовых типов, используемых в расширении, они присутствуют). Затем использовать FunctionCall интерфейс для вызова функции сравнения типа. Таким образом можно сократить функцию, избавиться от жестко заданных типов и повысить расширяемость, поскольку такая функция сможет сравнивать любые типы, для которых определена B-TREE функция сравнения.

Ссылки:
https://doxygen.postgresql.org/typcache_8h_source.html
https://doxygen.postgresql.org/typcache_8c.html#af52608205dff35bf1d467b3ea2a88814
https://doxygen.postgresql.org/arrayfuncs_8c.html#a86b86097da9f939df9a2cf1349b4bbd0 \[На данной странице можно посмотреть пример использования FunctionCallInfo для реализации сравнения Datum разных типов\]

- static Datum parse_item(const char *data, int len, int* pos, Oid item_type):
Функция решает сразу несколько проблем:
* управление состоянием парсера
* выборка константы
* приведение типов
* лексическая валидация константы
Предложение: можно попробовать разделить parse_item на несколько шагов, которые решают приведённые выше задачи. Таким образом, можно было бы улучшить читаемость отдельно взятого шага, облегчить расширяемость и поддерживаемость каждого шага, упростить отладку.
*Можно также попробовать завести ParserContext для состояния парсера. Таким образом можно упростить работу с его состоянием. Однако, пока состояние парсера описывается только одной переменной - позицией на строке, это излишне*

- static predicate_op parse_operation(const char *data, int len, int* pos):
Функция хорошая, решает поставленную задачу
*Предложение: однотипный код можно попробовать спрятать в макроопределение для сокращения длины функции, однако она достаточно читаема и без этого.*

- static predicate parse_predicate(const char *data, int len, Oid item_type):
Функция решает поставленную задачу.
Предложение: Функция решает сразу несколько проблем: лексический анализ, определение типа предиката и валидацию операций. Можно рассмотреть разделение ответственности для этих функций с теми же целями, что и в `parse_item`

- static bool process_predicate(Datum obj, Oid obj_type, predicate pred, Oid collation):
Функция хорошая, решает поставленную задачу.
Предложение: логику взятия остатка от деления можно вынести в макроопределение для упрощения чтения функции

## Производительность
### Алгоритмические решения
- Datum array_contain(PG_FUNCTION_ARGS):
На данный момент для поиска NULL функция предлагает алгоритмическую сложность O(n),
можно попробовать прийти к сложности O(1), используя ARR_HASNULL
- Datum array_contains_all(PG_FUNCTION_ARGS):
На данный момент алгоритмическая сложность составляет O(m * n), где m, n - длины массивов.
Плюсы такого подхода: всегда предсказуемая алгоритмическая сложность, нет затрат памяти на дополнительные структуры, нет лишних аллокаций.
Предложение: можно попробовать использовать хеш-таблицу для решения нахождения элемента, в таком случае можно сократить алгоритмическую сложность до O(m * h), где h - алг.сложность поиска в хеш-таблице, которая в среднем и лучшем случае составляет O(1). Однако данный подход требует дополнительной памяти. Можно написать реализацию на хеш-таблице и сравнить по производительности и потреблению памяти, после чего принять оптимальное решение. Либо можно попробовать сделать адаптивный алгоритм, который использует хеш-таблицу, пока наполнение второго массива не превысит k элементов.
Стоит обратить внимание: на маленьких n хеш-таблицу строить нет смысла, т.к. стоимость её построения будет перекрывать пользу.

Отдельно про поиск NULL: см. array_contain
